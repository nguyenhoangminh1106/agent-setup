# UI Test

Test the running UI against the walkthrough generated by `testing-instructions`.
Deliver evidence of what passed, failed, or could not be tested. This is a
testing-only workflow: do not fix code as part of it. Keep it reusable across
repositories: discover project-specific URLs, login methods, and data rather
than assuming a particular product or provider.

## Establish the work in scope

Use [current-work](../current-work/SKILL.md) to establish the requested feature/fix, baseline, and included changes. Reuse an existing scope result when it is still current; pass that result to downstream skills without broadening it. Keep this skill's task, permissions, and output format.

Do this before selecting tests. Include adjacent interactions only when the
scoped change plausibly affects their contracts, and explain that connection.
Keep the scope result available for reconciling or generating the walkthrough.

## Inputs and walkthrough

Use the app URL, database URL, target branch/PR, and walkthrough already supplied
in the request or conversation. Do not ask for information already provided.
Never save a database URL containing credentials in this skill or the report.

Before testing, discover which relevant tools are actually available: browser
control, desktop/OS UI control, mailbox inspection, native simulator/device
control, screenshot capture, and optional read-only DB access. Use documented
interfaces and respect each tool's access restrictions. A connector that reads
mail cannot by itself capture the mailbox UI; browser control cannot by itself
operate a native app. Do not install tooling to fill gaps.

Collect missing inputs together: existing app URL or mobile target, designated
test account/tenant, test mailboxes and recipients, permitted external actions,
and optional DB access. Reuse known inputs and authenticated test sessions;
never ask for passwords in chat. Ask only for inputs needed by the scoped flow.
Mark checks lacking tools, access, or setup Blocked and continue independent
checks. Do not make optional DB access a prerequisite for unrelated UI checks.

If a walkthrough exists, read its setup, steps, expected results, fixture SQL,
and gaps. Check it against the scope just established and the current code.
Retain relevant steps, omit unrelated ones with a brief explanation, and update
stale records or expectations using evidence. Preserve the ticket's intended
behavior when an instruction contradicts reliable product evidence. Explain any
expectation correction and its supporting requirement or product evidence; the
current implementation alone is not proof of intended behavior. Never weaken
an expectation merely to make an observed failure pass.

If there is no walkthrough, locate and read `testing-instructions` from the
session skill catalog or the sibling `../testing-instructions/SKILL.md`. Apply
it with the `current-work` scope result and supplied DB URL to generate
the plan first. Pass the available capabilities, designated test identities,
permitted actions, and existing-stack constraints too. Reconcile its output
with the channel checks below, adding only checks relevant to the scoped work.
Its branch-diff workflow must not broaden an explicitly narrow
target or turn imported main-branch work into new test obligations.
Reuse `query-db` for database inspection when available. Do not fetch Git refs
or change Git state merely to generate the plan; use local refs and disclose
any freshness limitation. If the required skill cannot be found, report the
missing dependency rather than inventing its instructions.

For web testing, use the existing app URL from the walkthrough, session,
running browser tab, or repository development documentation. If it remains ambiguous, ask for it.
If database access is needed and no URL was supplied, ask for the URL or whether
to proceed without DB verification. A supplied DB URL is not evidence that the
running UI uses that database.

## Existing server only

- Never start, restart, stop, replace, or spawn an application server, API,
  worker, container, database, proxy, tunnel, mobile development/bundler server,
  simulator, emulator, or other service. The user owns the running stack.
- For native testing, use an already-running simulator/emulator or connected
  test device with a test build installed and its backend already available.
  Do not build, install, or replace the app. Opening the installed test app is
  allowed; starting a simulator or development server is not.
- Do not run dev/start/bootstrap/migration commands, broad reseeding or resets,
  install dependencies, change environment files, or use a test runner that
  automatically launches a server. Targeted test-data setup belongs to
  [seed-data](../seed-data/SKILL.md) under the setup rules below; it must not
  start services or change their configuration.
- Opening a browser or a tab for the existing app is allowed. Use the available
  browser UI tooling and its documented APIs to test that app directly.
- If the app is unreachable, redirects to the wrong environment, or a required
  backend is unavailable, record the exact blocker and ask the user to restore
  their stack. Do not start a fallback server or substitute another deployment.

## Setup and authorization

Use only designated test accounts, test tenants/records, mailboxes, recipients,
and devices. A signed-in session or localhost URL does not establish that an
account is for testing. Verify the account, tenant, app/backend environment,
and integrations before actions; never run tests as a real user's account or
send to real users. Ask when test designation is unclear. A live email provider
is usable through designated test mailboxes; report it as a live-provider path.

Reuse a suitable authenticated test session. Follow the repository's login
skill when needed, explicitly selecting the designated test identity rather
than inheriting a default real user. It does not override the prohibition on
starting services or changing environment configuration.

Use read-only queries for inspection and persistence verification, scoped to
the test tenant and IDs. Do not replace UI actions under test with direct API
calls or SQL mutations.

If required records are missing, use [seed-data](../seed-data/SKILL.md) rather
than maintaining fixture setup SQL or declaring a fixable data gap blocked.
Pass the walkthrough, exact required states, designated identities, datastore,
verified app/backend relationship, and existing-stack constraints. Use execute
mode for minimal synthetic setup covered by this local UI-test request, unless
the user restricted writes; a DB URL alone is not authorization. Use plan mode
when the target or authorization is unresolved, then ask about that specific
gap. Reuse its IDs and verification results, resume the affected steps, and
coordinate cleanup after testing. Missing native/device/provider capabilities
remain separate blockers even when data can be seeded.

Perform the test UI actions authorized by the user's request. A localhost app
can still send real email, calendar responses, payments, or provider changes.
Before external effects, verify an established mock/sandbox boundary or obtain
explicit authorization for the concrete test recipients and actions. Establish
that permitted sequence upfront and reuse authorization while its scope holds;
ask again only if the recipient, action, or environment changes. Inspect all
recipients, including CC/BCC, reply-all participants, and calendar attendees.
Real-user recipients remain out of bounds for this skill. Do not treat the
generated walkthrough as authorization for external effects.

## Notification, email, and mobile checks

Select only channels affected by the scoped change. Put their preconditions,
exact test identities/records, trigger, expected results, and evidence in the
walkthrough before execution. Missing native or mailbox tooling must not
silently become a browser-only substitute.

| Channel | Preconditions and observable checks |
|---------|-------------------------------------|
| In-app notifications | Trigger an authorized event between test identities; check notification content, badge count, read/unread changes, destination, and persistence where relevant. |
| Browser/OS notifications | Verify app permission, OS/browser permission, and delivery setup. Exercise the specified foreground/background state; inspect the actual notification and its click destination through desktop tools. Do not claim OS delivery from an in-app toast. |
| Email / Outlook | Use designated sender and recipient test mailboxes. Trigger sends in the app UI, inspect receipt and rendered content in the recipient mailbox, then perform authorized replies through the mailbox UI and verify sync into the app when in scope. A mailbox connector may establish receipt but does not prove rendered UI layout. |
| Mobile web | Use browser viewport/touch controls supported by the tool; check scoped layouts, scrolling, keyboard, and interactions. Record emulation limits; this provides no evidence of native shell behavior or native push. |
| Native mobile | Verify the installed test build, device/simulator, OS, signed-in test identity, and backend. Use device UI tools for navigation, keyboard, permissions, background/foreground transitions, and deep links as scoped. Push tests require a working push path for that specific build/device; a local notification is not proof of remote push delivery. |

Change notification permissions only for the test app/profile/device as needed
by the authorized walkthrough. Never disable global OS protections or change
provider/push configuration. Record temporary permission changes and restore
those made by the test where supported; disclose any that remain.

For asynchronous flows, correlate a unique test subject or marker with the
trigger time and message/event ID where available. Use a bounded observation
window based on the walkthrough or known delivery behavior; report the actual
wait and outcome. Mark missing prerequisites Blocked; a working path that fails
its expected result within the window is Failed, with later delivery unresolved.
Do not repeatedly send events to force success. Verify trigger, delivery,
visible state, click/deep-link destination, and persistence as separate assertions
when required; passing one does not establish the others.

## Execute and verify

Follow the numbered walkthrough in order, with setup completed upfront and one
user session where possible. Use exact records and URLs from the plan and DB;
do not silently substitute different data or claim a blocked step passed.

For each step, perform the action, observe the result, and compare it with its
`Expect:` statement. Capture useful screenshots and available console/network
evidence for failures and important outcomes. Save representative screenshots
as local image files before closing tabs, with descriptive filenames identifying
the tested screen/state and viewport or device. Capture actual browser, desktop,
mailbox, and native screens only through tools supporting that surface. If a
surface cannot be captured, state the limitation; never fabricate a screenshot.
When a step asserts persistence, Undo, or a cross-screen update, verify that
contract with the UI and a scoped
read-only DB query where appropriate.

Exercise the phone/desktop sizes and keyboard interactions named in the plan.
Use temporary browser viewport overrides; restore them afterward. Test resizing
and pending operations without remounting controls or resetting state yourself.

Fixture setup through seed-data must precede the affected test steps. Do not
rewrite records after a failed assertion to force the expected result.

If a step fails, capture the actual state and stop dependent actions that could
compound or obscure the failure. Continue independent steps when safe. Retry
only when evidence identifies a transient problem; do not repeatedly click a
mutation or force success by editing data or code. Do not patch application
code, browser DOM/CSS, runtime state, or network responses to make a check pass,
or delegate repairs to another skill or agent. Report proposed fixes as
recommendations; implementing them requires a separate user instruction.

Judge visual expectations from the actual rendered UI and saved screenshots.
A visible mismatch with the expected layout, content, or state is Failed even
when an API call succeeds. If the evidence is insufficient to decide, mark
the assertion Blocked and state what is missing. Preserve the original failure
and evidence when an allowed retry passes; report both outcomes and the reason
for retrying instead of presenting an uninterrupted pass.

Distinguish a harness or mocked-provider result from the real app/provider path.
A simulated success or successful HTTP response alone does not establish that
the organizer received an answer or that data persisted correctly.

## Screenshot evidence

For an important visual transition, capture the relevant starting state before
acting and the resulting state afterward. Preserve enough context to identify
the same test record and the visible change; a counter alone is weaker evidence
than the named item changing alongside it.

For a comparison, use the same account/tenant, records, filters, screen,
viewport/device, and framing where possible. Disclose material differences;
counts from different datasets do not establish a change. Distinguish **before
and after the fix** (different code versions) from **before and after an action
or timed event** (one version). A successful transition on fixed code does not
prove that the old version was reproduced. Label historical/user-supplied
screenshots as context, separate from controlled test evidence. If a requested
baseline cannot be run under the existing-stack constraints, mark that check
Blocked; do not substitute an unrelated screenshot or change services to obtain it.

Before reporting, visually inspect the actual saved files selected for the
response. Check that the relevant item, count, message, or control is readable,
not clipped, and agrees with the caption and claimed result. Record actual
capture dimensions when they differ from the requested viewport. Recapture when
permitted and useful; otherwise narrow the claim to what is visible. Never
alter UI content in an image to make the evidence fit.

## Report

Report the tested scope and its Git baseline, the tested URL, branch/commit,
designated test account/tenant, and tested viewport sizes. For native tests,
include device/simulator, OS, app build/version where available, and backend.
Identify tested channels and unavailable capabilities, scoped working-tree
changes, and any walkthrough steps omitted as out of scope.
Show the DB host/database without credentials when DB checks were used.

Use a compact results table:

| Step | Expected result | Observed result / evidence | Status |
|------|-----------------|----------------------------|--------|

Statuses are **Passed**, **Failed**, or **Blocked**. Show the read-only queries
with their relevant results. Summarize actual failures, outstanding setup or live
provider checks, and any test-created records that remain. Do not label the
feature fully verified while required steps remain Failed or Blocked.

Include the strongest supporting test photos directly beside the corresponding
claim in the final summary using Markdown image embeds, not only links to a
report or images in tool output. For a claimed transition or requested comparison,
show the matching pair together in chronological order with specific captions
such as "Before action: test record pending" and "After action: same record
completed"; include the observed counts when they support the assertion. Do not replace that pair with a historical
image or a different viewport's overview. Choose evidence for important outcomes
and failures rather than every click. Caption each image with its test step,
screen/state, actual viewport or device, and whether it shows the running app,
live test mailbox/provider, simulator/device, or harness. Keep credentials and
unrelated personal content out of captures; do not publish evidence automatically.
Use absolute local paths for chat embeds and link the corresponding evidence
from the results table. Images support only the state they visibly demonstrate;
keep blocked delivery, persistence, and Undo checks explicit.

Also save a concise PR-ready Markdown summary beside the images, containing
the tested commit/environment, results table, remaining gaps, and the same
captioned evidence pairs used in the final response. Link it in the final
response. Use relative image filenames in
this saved summary so the evidence folder remains portable. Explain briefly
that local image paths do not render on GitHub: the user must upload/drag the
images into the PR editor and use the resulting GitHub attachment URLs. Reuse
already available authorised attachment URLs when present; do not upload or
publish screenshots solely to produce this summary. If no screenshots could
be captured, state why instead of fabricating photo evidence.

Leave the user's services and configuration alone, apart from documented
temporary test permission changes restored as above. Leave pre-existing mobile
apps and devices running. Close disposable browser tabs and restore temporary viewport overrides according to browser-tool policy.
